# USRP Overflow 对 BER 测量的影响及工程处理

日期：2026-03-28

---

## 背景

RX 端命令行出现如下提示时：

```
usrp_source :error: In the last 19249 ms, 1 overflows occurred.
```

表示主机侧未能持续接收 USRP 样本流，采集中间发生了丢样或时间连续性破坏。

**MATLAB 端常见表现：**
- 某个时间点之后 BER 突然整体抬升
- Tracking 状态图中频率估计或相位误差在对应时刻出现尖峰
- `reacq_events` 明显增多
- 前半段正常、后半段突然失稳

---

## 核心问题：长时测试（如 1 小时）难免出现 overflow，如何处理？

### 定量分析：overflow 对 BER 的实际污染量

即使只有 1 次 overflow，影响也可能非常显著。以典型参数为例：

```
BER 目标 = 1×10⁻⁵
bit rate = 1 Mbps
测试时长 = 1 小时

总 bits ≈ 3.6 × 10⁹
目标错误数 ≈ 36,000

1 次 overflow 导致 5 秒跟踪失锁：
  坏 bits = 5 × 10⁶
  额外误码 ≈ 2.5 × 10⁶  （失锁期间 BER ≈ 0.5）

污染后 BER ≈ (36,000 + 2,500,000) / 3.6×10⁹ ≈ 7×10⁻⁴
```

**结论：即使只有 1 次 overflow + 5 秒失锁，测出来的 BER 就已经比真实值高约 70 倍。**

## 工程实际处理方式

### 实际上，多数工程师不分段，直接跑，看结果是否"够好"

不分段时，实际结果分两种：

| 情况 | 实际表现 | 通常处理 |
|------|----------|---------|
| overflow 发生时 RX 跟踪未失锁（缓冲来得及补） | BER 曲线无明显异常 | 接受结果，加注脚说明 |
| overflow 导致失锁/重捕获 | BER 曲线有明显尖峰，整体均值被抬高 | 本轮作废，必须重测 |

### 工程底线做法

1. **看 BER 时序曲线**，不只看均值
   - 有没有明显尖峰？
   - 尖峰时刻与 overflow 日志时刻是否对得上？
2. **如果对得上，且 BER 均值明显异常** → 作废重测
3. **如果对不上，BER 曲线平稳** → overflow 未影响跟踪，结果可信
4. **正式验收测试**（交付、论文、合规）→ overflow = 无效，必须重跑，无例外

## 分段隔离方案（用于自动化测试框架）

对于需要自动化处理的场景，可使用分段标记 + overflow 隔离窗的方式：

- 将测试切分为若干短段（如每段 30s ~ 1min）
- 每段独立记录是否出现 overflow 及发生时刻
- overflow 前后各设置隔离窗（建议 ±5s，视环路带宽调整）
- BER 统计只聚合无 overflow 的干净段

**overflow 影响范围经验值：**

| 现象 | 典型扩散范围 |
|------|-------------|
| 缓冲区打满、丢包 | 通常 < 1s |
| 跟踪环失锁、重捕获 | 通常 < 5s |
| 相位/频率误差恢复 | 几百 ms ~ 数秒（视 PLL/DLL 带宽） |

**报告格式示例：**
```
有效采样时长:  3547 s / 3600 s
Overflow 事件: 3 次（已各隔离 ±5s 窗口）
剔除时长:      53 s（占比 1.5%）
有效 BER:      x.xx × 10⁻⁵
```

> 注：分段隔离方案在自动化测试框架中有用，手工测试中通常不做。

## 根本解决方案

与其设计复杂的补救逻辑，更推荐从源头消除 overflow：

### 优先：先录后算

```
USRP → 流存磁盘（.fc32 / .sc16）→ 离线 MATLAB 处理
```

录制阶段只做最简单的 I/O，几乎不会 overflow；处理阶段完全离线，无实时压力。**长时 BER 测试的推荐架构。**

### 其次：实时采集优化

- 增大 USRP 缓冲区参数
- 降低主机侧实时处理负载（关闭无关进程）
- 有条件时换用 10GbE 接口替代 USB3

---

## 小结

| 场景 | 推荐处理 |
|------|---------|
| 开发调试 | 看曲线判断，overflow 未致失锁则接受，加注脚 |
| 研究记录 | 同上，BER 时序图存档，注明 overflow 事件 |
| 正式验收/交付 | overflow = 无效，必须重测 |
| 长时自动化测试 | 改为"先录后算"架构，从根本上避免问题 |
